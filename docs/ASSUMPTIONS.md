# Assumptions

- ASSUMPTION-001: An officer belongs to one branch at a time.
- ASSUMPTION-002: A loan has at most one active officer assignment per day.
- ASSUMPTION-003: Indore business dates use Asia/Kolkata; stored timestamps are timezone-aware UTC.
- ASSUMPTION-004: Demo credentials exist only for local synthetic-data evaluation.
- ASSUMPTION-005: Stage 1 seeded priority scores are deterministic representations, not model output.
- ASSUMPTION-006: The canonical CSV headers are `loan_id`, `borrower_name`, `outstanding_amount`, `dpd`, and `pincode`; optional fields are documented in the sample file.
- ASSUMPTION-007: An identical confirmed file is idempotent. A conflicting same-day snapshot is rejected and must be corrected in the source file before a fresh preview.
- ASSUMPTION-008: Automatic assignment has no unsupported-pincode fallback. Such loans remain unassigned for manager review.
- ASSUMPTION-009: Assignment cost is the sum of normalized account count, outstanding exposure, and accounts at 30+ DPD; user ID is the stable tie-breaker.
- ASSUMPTION-010: Manager reassignment requires a reason and an active in-branch officer who covers the borrower pincode.
- ASSUMPTION-011: One open promise per loan is allowed. A new promise outcome is rejected while another promise remains open.
- ASSUMPTION-012: A reported PAID outcome is operational evidence only and never changes authoritative loan outstanding.
- ASSUMPTION-013: OPEN promises are deterministically reconciled to BROKEN when read or changed after their due date in the branch timezone.
- ASSUMPTION-014: KEPT requires an explicit mock verification action by an authorized officer or manager; the reason and transition are retained.
- ASSUMPTION-015: In-app CALL and MESSAGE initiation is allowed from 08:00 inclusive to 19:00 exclusive in the branch timezone.
- ASSUMPTION-016: Browser location denial, timeout, low accuracy, or unavailability does not discard an outcome; the location status is persisted for review.
- ASSUMPTION-017: Roll rate uses consecutive monthly snapshots 28–32 days apart. The denominator is the initial 1–30 DPD cohort; missing follow-up loans are disclosed and remain in the denominator.
- ASSUMPTION-018: Reminder delivery is a labelled simulation. No SMS or WhatsApp provider is contacted in Stage 2.
- ASSUMPTION-019: Seeded historical snapshots and coordinates are synthetic demonstration records.
- ASSUMPTION-020: Reported and promised amounts cannot exceed the latest authoritative outstanding balance.
- ASSUMPTION-021: Protected offline queues are unlocked only after the current browser session has been verified online; a fresh offline restart requires reauthentication.
- ASSUMPTION-022: IndexedDB stores only scoped loan and promise summaries plus unsynchronized event payloads. It is not encryption at rest, so shared-device residual storage risk remains.
- ASSUMPTION-023: Logout clears cached portfolio and promise projections but retains isolated unsynchronized outbox events so field work is not silently destroyed.
- ASSUMPTION-024: Outcome synchronization requires the cached assignment version to equal the current active assignment version. A mismatch is retained as a conflict and never force-applied.
- ASSUMPTION-025: Server-rejected and conflicting device events are terminal records until an officer explicitly discards them; network failures remain retryable.
- ASSUMPTION-026: Foreground reconnection is the reliable synchronization mechanism. Browser Background Sync is not claimed across all Android browsers.
- ASSUMPTION-027: Priority risk is a class-balanced, regularized logistic model trained on stored 28–32 day snapshot transitions from 1–30 DPD into 31–60 DPD.
- ASSUMPTION-028: Model validation uses the latest 20% temporal holdout, with at least four observations, and reports AUC, accuracy, precision, recall and Brier score without fabricating unavailable metrics.
- ASSUMPTION-029: Priority reasons are the three largest positive standardized feature contributions, translated into controlled business-language explanations rather than SHAP values.
- ASSUMPTION-030: A manager rank override changes operational ordering but does not overwrite the model score; the rationale and version are retained for audit and back-testing.
- ASSUMPTION-031: Reminder drafting uses approved bilingual templates with controlled variable substitution and mandatory human review. It is not presented as unconstrained generative AI.
- ASSUMPTION-032: Login throttling is process-local in the modular monolith; a production multi-instance deployment should move the counter to shared infrastructure such as Redis.
- ASSUMPTION-033: A persisted `SYNCING` outbox event may be safely replayed during foreground recovery because the server receipt is keyed by immutable client event UUID.
- ASSUMPTION-034: Hindi support in Stage 4 covers the officer navigation, queue, common outcome flow, sync states and contact notice; manager operations remain English-first.
- ASSUMPTION-035: The public deployment URL is intentionally omitted until the repository owner supplies hosting credentials and approves a live synthetic-demo deployment.
